# council.html Changelog

This is a separate changelog from `CHANGELOG.md`, which tracks `test.html` (legislative-district map) only — `council.html`'s development had never been logged anywhere until this file was created. Entries before today are summarized in aggregate from what's independently verifiable (data files, code comments, prior session memory); entries from today onward are logged at normal per-fix granularity going forward.

## Pre-existing, undated — baseline feature set

Before this changelog started, `council.html` already had: county/city councilor (縣市議員) and mayor (縣市長) maps for 2014/2018/2022 with party-vote/candidate-mode coloring, township and village drill-down, 原住民 (indigenous) seat panels, and a 2026 mayor-election prediction mode (poll aggregation blended with historical anchors via `regen3.py`, Monte Carlo simulation for vote-share ranges and win probabilities, poll-tracking and approval-rating trend charts, a daily snapshot log for tracking the model's own output over time). See `README_council.md` for the current architecture.

## 2026-08-17 — 新竹市 split-township data corruption (multi-part bug, found via user-reported black screen)

User reported council districts 第2/第4選舉區 in 新竹市 rendering as a black screen in 2018 council mode. Root-caused to four compounding issues, none of which were about the map geometry (an early hypothesis — deleting "phantom" district features from `council_dist_gj.js` — was wrong and reverted):

1. **`build_council_multi.py` was summing two different real people's votes together.** 新竹市's 東區/北區 townships are each split across two council districts nationally-uniquely; candidate numbers are assigned independently per district, so "candidate #3 in district 01" and "candidate #3 in district 02" are unrelated people who happened to draw the same ballot number. The build script keyed vote aggregation by bare township code, silently merging them. Fixed by keying by `(township, district)` during aggregation, and adding a real per-candidate/per-village `d` (district) field to the output so the front end never has to re-derive it.
2. **`getCouncilDistData()` looked up a district's data by filtering townships on their single `.dist` field.** A merged split-township can only hold one of its two districts there, so the non-primary district's lookup always returned nothing (or fell back to showing the *other* district's data — the "district 2 shows district 1's data" bug the user caught via screenshots). Rewritten to aggregate by each candidate's own `d` field instead.
3. **`buildCouncilIndexes()` had a permanent one-time-build guard.** `_vcToDistKey` etc. were built once (typically from whichever year loaded first, usually 2022) and never rebuilt on year switch — stale village→district mappings for every other year. Now tracks `_councilIndexedYear` and rebuilds when `councilDisplayYear` changes.
4. **Village-level vote totals were exactly doubled, for every village, every year — unrelated to the split-township issue.** CEC's raw `elctks.csv` lists both a village-aggregate row (`polling='0'` for 2014/2018, `'0000'` for 2022) and one row per individual polling station within that village; the parser summed all of them. Found via a concrete discrepancy (a candidate's authoritative district total was 5,155, confirmed two independent ways, but the buggy village-level sum was 10,310 — exactly 2×). Fixed by filtering to the aggregate-row `polling` value only.

Also found and fixed while investigating: `_buildCCSeatCache()`/`_buildCCDistOffsets()` had the same "enumerate by `.dist`" blind spot, silently never visiting a split township's secondary district when building county-wide seat totals (the *total* happened to still be right, by coincidence of how votes got misattributed — but the per-district breakdown and hemicycle highlighting were wrong).

All four fixes validated against raw CEC ground truth: zero mismatches across all 368 townships × 3 years (seat counts, elected-candidate counts, vote totals), plus a new check confirming village-level totals now correctly sum to their township's total.

## 2026-08-18 — Second, much larger English translation pass

Live testing in `currentLang='en'` surfaced far more untranslated Chinese than the 08-17 pass caught — candidate cards, poll-source notes, president/premier approval charts, the county ticker buttons, and more. Root cause was structural, not just missed strings: **`applyLang()`'s "redraw right info panel" logic was written entirely for the legislative (`test.html`-inherited) DOM shape** — it re-triggers by dispatching synthetic `mouseover` on `.ft-ed[data-ed]`/`.ft-tc[data-tc]` elements, which don't exist in council/mayor mode's map layer, so it silently no-op'd. Fixed by adding a mayor/council-aware branch to `applyLang()` that re-invokes the correct panel-html function based on current `level`/`curED`/`curTC`/`curVC` and rebuilds the breadcrumb.

Also: converted `COUNCIL_LBL` and `_CC_NAME` (flat Chinese-only lookup objects used at dozens of call sites) to bilingual via a `Proxy` wrapper keyed on `currentLang`, rather than touching every call site individually. Added `_dispCandName()` to handle `MAYOR_2026_PREDICT`'s baked-in candidate label format (`"吳秀華（民調樣本少...）"` — name plus a Chinese methodology note); translates the name, drops the note in EN mode (translating the note itself is out of scope). Verified via a regex sweep of lines 359900–372697 for untranslated Chinese inside HTML tag contexts: 38 hits → 5 (4 false positives, 1 real fix applied).

**Known remaining gap** (unchanged from 08-17): `POLL_HOUSE_LEAN`'s ~35 per-pollster sourcing notes are still Chinese-only.

## 2026-08-18 — Added a real uncertainty band to president/premier approval trend charts

User asked to bring the vote-share trend, poll chart, and approval charts to the same "range" treatment. Investigating turned up that `_renderApprovalTrendSvg` was, despite an internal variable named `bandSvg`, only ever drawing the smoothed **mean line** — no actual shaded band — unlike `_renderPollLineChartSvg`, which already computes a proper weighted mean ± weighted-standard-deviation band from the scatter of individual polls via a Gaussian time-kernel. Extracted that kernel math out of `_renderPollLineChartSvg`'s local `_gaussTrend` closure into a shared top-level `_gaussTrendStats(series, tMin, tRange, bwMs, getVal)`, and used it in `_renderApprovalTrendSvg` to draw a real shaded band (mean ± sd) for all three series (approve/disapprove/undecided), matching the poll chart's visual weight (fill opacity 0.16, stroke-width 2). Updated the approval card's legend text to describe the band. Verified the poll chart's own output is byte-for-byte unaffected by the refactor (same band/line/dot counts and fill colors as before).

Also bumped the vote-share median (`pct50`) trend chart's line/band visual weight (stroke-width 2, band opacity 0.16) to match the other two charts for visual consistency — its underlying mechanism (piecewise-linear band between consecutive days' real `pct10`/`pct90` from the model) is left as-is, since that's a more principled uncertainty source for this data than a fabricated cross-day statistical spread would be.

## 2026-08-18 — 連任幾屆／新選上 badge for council candidates

User asked whether the councilor mode could show incumbency (連任幾屆 / newly elected) without adding visual clutter. Implemented using the three already-loaded election-year datasets (`COUNCIL_2014_TC`/`COUNCIL_2018_TC`/`_COUNCIL_2022_TC_ACTUAL`): for each elected candidate in the currently displayed year, walk backward through consecutive prior cycles checking whether the *same name won anywhere in the same county* (not the same district — district numbering/boundaries aren't stable across 2014→2022, see `_buildCCSeatCache`'s existing comment on this), stopping at the first miss. A candidate elected in 2022+2018+2014 shows `×3`; a first-time winner (relative to the dataset) shows `新`/`NEW`; 2014 itself never shows a badge since there's no earlier cycle to compare against.

Sanity-checked the underlying logic against real-world knowledge before touching the UI: Taipei's known multi-term councilors (王鴻薇, 許淑華) came back as 3-term winners, as expected. First implementation attempt appended the badge text directly inside `.blb` (the candidate-name cell) — but that cell is a hardcoded 70px `overflow:hidden;text-overflow:ellipsis` box (in `style.css`), so the badge got clipped mid-text ("連2...") for almost every row, exactly the clutter/breakage the user was trying to avoid. Fixed by moving the badge into its own small fixed-width flex cell in `.bar-row`, always rendered (even empty) for council-mode rows so the vote bars stay aligned whether or not a given candidate has a badge. Only fires when the caller passes a `cc` (county code) into `renderCouncilCandRow()` — mayor-mode and other reused callers of this function don't pass it, so they're completely unaffected. Wired into all three council panel levels (ED/TC/VC). Tooltip on hover explains the "tracked from 2014 only, actual tenure may be longer" caveat rather than presenting the term count as precise career history.

Follow-up fix (same day): user reported the `×2`/`×3` badge text rendering vertically (one character per line) instead of horizontally — the slot's 16px width was narrower than "×2" needs, so the browser wrapped it mid-text. Fixed by widening the slot to 20px and adding `white-space:nowrap` to both the slot and the inner badge span.

## 2026-08-18 — Candidate translation: replaced curated-map-only with a pinyin CDN fallback (closes a ~2,600-name gap)

User reported many candidates in council mode still untranslated in EN mode, including 陳其邁 (Kaohsiung's own mayor — about as high-profile as it gets). Measuring the actual gap: `candidateTranslationMap` (the hand-curated ~700-entry map used since the first translation pass) covers only a fraction of the real universe — across 2014/2018/2022 council races alone there are 10,435 candidate rows spanning 2,618 unique untranslated names (1,096 unique Chinese characters). Hand-curating entries one at a time (the approach used for the earlier ~56-name and ~161-name gaps) does not scale to this — continuing that way would mean thousands more manual entries with real risk of transcription errors at that volume.

Replaced the approach: added `pinyin-pro` as a CDN script (`https://cdn.jsdelivr.net/npm/pinyin-pro/dist/index.min.js`, ~317KB minified, cached — doesn't add to `council.html`'s own file size, which the user separately flagged as already too large), loaded alongside the existing D3/topojson CDN scripts. `translateCandidate()` now tries the curated map first (preserving existing, sometimes-more-authentic entries like "Jiang Wan-an" for 蔣萬安 over what pinyin-pro alone would produce), and falls back to a new `_pinyinNameFallback()` for anything not in the map — converts to toneless Hanyu Pinyin, first syllable = surname (capitalized), remaining syllables = given name (first capitalized, rest lowercase, hyphen-joined), matching the curated map's existing style convention (e.g. "Chen Qi-mai", not "Chen Qi-Mai"). Known limitation, stated in a code comment: compound two-character surnames (歐陽, 司馬, etc.) will be mis-split since the heuristic always treats only the first syllable as the surname — accepted as a rare edge case rather than added complexity to detect them.

Verified via full sweep: 0 remaining untranslated names across all 10,435 council candidate rows (3 election years), 0 across all `COUNCIL_MAYOR_2022` mayors, and 0 across both indigenous-seat modes in all 22 counties — this incidentally also fully closes the ~161-name indigenous-candidate gap that had been explicitly deferred in the previous translation pass. Confirmed ZH mode is unaffected (still returns original names) and no console errors on a clean reload.

## 2026-08-18 — 平地/山地原住民 toggle buttons untranslated, including a click-resets-language bug

User reported the Plains/Mountain Indigenous toolbar toggle buttons stayed Chinese in EN mode. Two separate bugs: (1) the buttons' initial markup had the label as a bare string, not wrapped in the `<span data-zh data-en>` pattern the app's generic language-refresh handler (`document.querySelectorAll('[data-zh][data-en]')`) depends on — sibling buttons in the same toolbar already used this pattern, these two didn't; (2) worse, `setCouncilIndMode()`'s `_setBtn()` helper — which runs every time either button is clicked, to redraw the ◉/○ fill state — overwrote the button's entire `innerHTML` with a hardcoded Chinese string, so even after fixing (1), the very first click would wipe the translation back to Chinese. Also found and fixed a third instance of the same underlying issue in `_addCouncilIndLayer()`'s own separate `modeLabel` (used for the map-hover info panel, a different code path from the one fixed in the previous translation pass) — same hardcoded string, now `T()`-wrapped. Verified: button text stays in English through repeated on/off clicks, no console errors.

## 2026-08-18 — Marked candidates who came back and won after previously losing

User pointed out the winner-side badges had a gap: `_councilTermCount` returning `terms === 1` was always rendered as `新`/`NEW` (first-time winner), but `terms === 1` only means "not consecutive with the immediately preceding cycle" — it says nothing about whether the candidate won some *earlier*, non-adjacent cycle. `_councilTermCount`'s backward walk deliberately stops at the first non-win (documented reasoning: needed for the term-streak count itself), so it was silently treating a real comeback the same as a true first-timer.

Added `_councilWonAnyEarlierCycle(cc, name)` — scans every cycle before `councilDisplayYear` (not just the immediately preceding one, unlike `_councilWasIncumbentLastCycle`) for a win. When a `terms === 1` winner has one, they now get a purple `回鍋`/`BACK` badge instead of the green `新`/`NEW` one — distinct color from all three existing badges (gold `×N` consecutive, green `新` genuinely new, red `OUT×N` lost re-election). Verified against a real case (李雨庭 in Kaohsiung district 11: won 2014, lost 2018, won 2022 — correctly shows `回鍋`/`BACK`, not `新`/`NEW`) in both languages.

Follow-up fix (same day): user noticed the `BACK`/`OUT×N` badges' border was slightly overlapping the party icon next to it. Root cause: the 28px slot from the earlier OUT-badge fix was sized against a rough estimate, and the slot `<div>` had `white-space:nowrap` but no `overflow` set — so when the actual rendered badge (border + padding + text) came out wider than 28px, it didn't wrap or get clipped, it just visually bled past the box edge into the next flex sibling (the party icon). Widened the slot to 36px, which comfortably fits the longest cases ("OUT×3", "BACK") with margin to spare. Verified: clean gap between badge border and icon in both languages, no console errors.

## 2026-08-18 — Seat-cutoff divider line in the ED-level candidate list

User asked (after a back-and-forth about why some districts show a mix of `OUT`/`新` badges — explained that's normal, since council seats are multi-seat SNTV and Taiwan periodically reapportions seat counts per district between cycles, confirmed with real Kaohsiung examples where the same district held 6, 8, or 9 seats across 2014/2018/2022) whether the checkmark-per-row could be supplemented with a single divider line between the last elected candidate and the first non-elected one, to make the seat cutoff visible at a glance. Recommended keeping the checkmarks (they're still useful for identifying a single row's status in isolation, e.g. on a panel that doesn't show the whole list) and adding the divider as a complement rather than a replacement — user agreed.

User specifically asked to scope this to the ED-level panel only, not TC/VC. ## 2026-08-23 — Independent US-election validation of the predict methodology, then a real fix it led to: 新竹縣 no longer uses a stale/broken anchor

## 2026-08-23 — New feature: township-level vote-share/win-probability trend chart (derived, not independently tracked)

Previously flagged as a pending task (2026-08-16) and blocked on `MC2026_SNAPSHOT_LOG` having too few days to be worth building — now has 6 daily snapshots (08-15/17/18/20/22/23), enough to revisit. Built per the design already decided back then: **no second per-township snapshot log** (townships have no independent daily poll source — a separately-tracked township log would be fabricating data that was never actually measured that day). Instead, added `_deriveTownshipTrendEntries(tc)`, which for each day already recorded in `MC2026_SNAPSHOT_LOG`, backs out what that township's number would have been using a **relative-swing** approach: `derived_township_pct(date) = current_township_pct − (current_county_pct50 − snapshot_county_pct50(date))`. This is deliberately relative to *today's* township value (from `MAYOR_2026_PREDICT_TC`, whatever methodology built it — candidate-swing for most counties, party-swing for 新竹縣 per the fix directly above) rather than re-deriving each day from scratch, so the trend function doesn't need to know or care which swing methodology a given county's "current" township number was built with.

Win probability per derived point is an analytic normal-CDF approximation (`_erf`/`_normalCdf`, Abramowitz-Stegun approximation, error <1.5e-7) applied to the derived two-candidate margin, using the same combined SD (`_MC2026_COMBINED_SD` = √(2.94²+3.24²+4.41²) ≈ 6.21, matching the county-level σ) already used by `_runMCTownship()` — not a fresh 20,000-sample simulation per historical point per township, which would be needlessly slow for a value that's mathematically equivalent (same closed-form-vs-simulation equivalence already established by `backtest_montecarlo_vs_analytic.html`).

`_renderTownshipMC2026TrendHtml(tc)` wraps this and reuses the *exact same* `_mc2026TrendLineSvg()` renderer the county-level trend chart already uses (same chart component, tooltip interaction, and — automatically, with no extra code — the `MC2026_MODEL_REVISIONS` dashed-line marker), just fed derived instead of directly-logged entries. Wired into `_mayorTcPanelHtml`'s predict-mode branch as a new collapsed-by-default `_predict26Fold` section, right after the candidate vote rows. Carries its own explicit "this is derived, not independently measured" warning box, separate from the general township-uncertainty warning already shown above it.

Verified live for 10004010 (竹北市): 6 derived days render correctly, the chart correctly shows the dramatic crossover right at the 2026-08-23 revision marker (徐欣瑩 leading ~59% pre-fix → 鄭朝方 leading 52.39% post-fix) with the calibration dashed-line clearly separating the two eras, and the last derived point (2026-08-23) exactly matches the current live `MAYOR_2026_PREDICT_TC` value by construction.
